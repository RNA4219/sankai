# 分解

元スキルを仕事の単位に分け、それぞれを担う指示本文を取り出す。本文と必要条件を一緒に持ち出せることを成果とする。

## 分ける単位

ファイルや見出しをそのまま単位にせず、仕事・判断・条件の切れ目を探す。前提、入力、出力、道具、権限、作用が変わる場所は境界の候補になる。単独では条件が欠ける指示や例外は、対応する部分との関係を残す。細かくする理由がなければ元のまとまりを保つ。

各候補について「何を受け取り、何をして、何を返すか」を原文から押さえる。入力や成果が未定義ならそう記し、都合のよい契約を作らない。同じ仕事に必要な指示が複数ファイルに散っていれば結び付け、一つの節に別の仕事が混在すれば分ける。

スキル本体から参照資料・スクリプト・素材へのつながりをたどり、その仕事に必要なものを特定する。参照先は元の基準位置から解決し、取り出した先で切れない形で示す。未取得・未同梱を、独立して使える状態と見なさない。分解だけの依頼でスクリプトや外部操作を実行しない。

| 役割 | 読み取ること |
|---|---|
| 作業 | 何を行い、何が得られるか |
| 適用条件 | いつ、誰・何に対して使うか |
| 品質制約 | 作業や結果が満たす条件、禁止、許容範囲 |
| 検証 | 何を観察すれば条件を確かめられるか |
| 参考例 | 何を例示しているか、例の有効範囲 |
| AI運用 | エージェントの報告、確認、読込み等の運用方法 |

役割は排他的とは限らない。たとえば承認を求める記述は、公開条件にもエージェントの作業運用にもなり得る。語句や見出しだけで判断せず、対象と働きを読む。

この役割表は指示を読むための分類であり、出力を6つのスキルへ分ける指定ではない。品質制約や例外は、それが掛かる仕事から切り離さない。

## 残す関係

適用条件、前提、参照、正本への委任、例外、検証方法を区別する。単に言及されている資料を、すべて実行の必須依存に変えない。まだ読んでいない参照先は、名前と未取得の状態だけを残す。

例外は「元の規則のどの項目を、どの条件で変えるか」まで対応づける。例外が一項目に掛かっているとき、元の規則全体を取り消さない。複数の経路で同じ制約が働く場合は、各経路との関係を残す。

AI運用を別管理する依頼なら、原文の位置とともに選択・除外・未選択を区別する。未選択の運用を現在の作業へ適用せず、品質制約中の承認や停止まで外さない。

## 返し方と照合

取り出した仕事ごとに、名前と用途に続けて**指示本文**を置く。使う場面・入力・得られるもの、適用条件・例外、一緒に必要な指示・資料、出典を、読める最小限の形で添える。「認証を扱う」「検証する」等の役割名や要約だけでは本文の代わりにならない。

本文は原文の該当指示を抜き出すか、対象・強さ・条件を保って読み通せる指示に整える。逐語引用と編集した指示を区別し、変更可否の判断は溶解で照合する。複数の仕事に掛かる共通条件は一度記し、各仕事から明示して参照する。利用先でもその共通条件が必要なことを残す。

たとえば「Web告知とメール案を作る」スキルなら、Web作成とメール作成を候補にし、両者に掛かる事実確認・公開条件は共通として結ぶ。Webだけ取り出す場合も、関連する禁止や例外は本文に残す。成果物の種類が違うだけで必ず分割する規則にはしない。

一文書で足りれば分割ファイルや各部分の`SKILL.md`を増やさない。単独で使える部分、依存先と一緒なら使える部分、未確認のため切り出し可否が決まらない部分を示す。必要な条件を落として独立したように見せない。

元の条件がどこに残ったか、単独にした部分が前提を失っていないか、例文を義務にしていないかを原文へ戻って確かめる。目的の説明や変更可否の判断は、理解・溶解の結果とつなげる。

取り出した仕事に残る外部送信・保存・状態変更と、その説明や制限も原文から照合する。今回その仕事を実行しないことと、利用時の作用を指示本文から外してよいことを混同しない。
